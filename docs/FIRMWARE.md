# Firmware

The firmware in `firmware/` is an STM32CubeIDE project called `Atlas` for the NUCLEO-F446RE (STM32F446RE, 180 MHz from the ST-LINK's 8 MHz clock). It uses the ST HAL from STM32Cube FW_F4 V1.28.3, generated with STM32CubeMX 6.18.1. The build in the paper used 33,844 bytes of flash (6.5 % of 512 KB) and 1,880 bytes of RAM.

## What is in the project

| Path | Contents |
|---|---|
| `Core/Src/atlas_app.c`, `Core/Inc/atlas_app.h` | The tester: pin control, serial protocol, standalone test, OLED screens, LEDs, button, I2C recovery |
| `Core/Src/main.c` | CubeMX-generated start-up code; calls `App_Init()` once and `App_Loop()` forever from its `USER CODE` sections |
| `Core/Inc/ic_table_*.h`, `ic_table_common.h` | Generated by `software/generate_ic_tables.py`: compacted vectors, fault dictionary and golden responses for each chip. Do not edit by hand. |
| `Core/Src/ssd1306.c`, `ssd1306_fonts.c`, `Core/Inc/ssd1306*.h` | SSD1306 OLED driver from [afiskon/stm32-ssd1306](https://github.com/afiskon/stm32-ssd1306) (MIT), set up for I2C1 at address 0x3C |
| `Atlas.ioc` | CubeMX pin and clock configuration |
| `Core/Startup/`, `*.ld` | Start-up assembly and linker scripts |
| `Drivers/` | ST HAL and CMSIS, under ST's licences |

The application code lives outside `main.c`, so regenerating code from `Atlas.ioc` in CubeMX does not overwrite it. CubeMX names the fault LED `LED_FAULT1` in `main.h`; `atlas_app.c` accepts that name.

## Build and flash

1. Install STM32CubeIDE (any recent version with the STM32F4 package).
2. File > Import > General > Existing Projects into Workspace. Select the `firmware` folder as the root directory and finish. The project appears as `Atlas`.
3. Project > Build Project. The Debug configuration writes `Debug/Atlas.elf`.
4. Connect the NUCLEO to the PC with a USB cable on the ST-LINK connector.
5. Run > Run As > STM32 C/C++ Application (or Debug As, to step through the code). Accept the default ST-LINK settings.
6. After a reset, the OLED shows `READY`, and the virtual COM port prints `ATLAS-DIAG ready` followed by `OLED:OK` (or `OLED:NOT FOUND (check SDA/SCL/VCC)`).

STM32CubeProgrammer can also load the `.elf` if you prefer not to use the IDE for flashing.

If you change the chip models in `software/digital_twin.py`, run `python generate_ic_tables.py` from `software/`. It rewrites the headers in `firmware/Core/Inc/`; rebuild and flash afterwards.

## Standalone use

Power the board from a PC or a USB power bank. No PC software is needed.

| Action | Result |
|---|---|
| Tap the button (shorter than 1 s) | Selects the next chip: 74HCT00, 02, 04, 08, 32, 86, then back to 00 |
| Hold the button for more than 1 s | Runs the test on the selected chip |

Both the external button on PA10 and the on-board B1 button work. The OLED has four lines: `ATLAS-DIAG`, the selected chip (`IC:74HCT00`), a large status word, and a detail line.

| Status | Detail line | LED | Meaning |
|---|---|---|---|
| `READY` | `Tap=IC  Hold=Test` | none | waiting |
| `TESTING` | | LD2 blinks | test running |
| `PASS` | `256/256 OK` (or `64/64 OK`) | green | every input combination matched the twin |
| `FAULT` | fault name, e.g. `G4 OUT stuck-LO` | red | behaviour matches one single stuck-at fault |
| `FAULT` | names that change every 1.5 s | red | behaviour matches an equivalence class; the OLED cycles through every member |
| `FAULT` | `Bad n/N` | red | the full check failed and no single stuck-at fault explains it (missing power, bridged pins, a different chip, or several faults) |

A full test (both stages) takes about 1 s. If a PC is connected, the board also prints a one-line log for each standalone test, for example:

```
IC:74HCT00 RESULT:PASS FULL:256/256 SIG:000011111111
IC:74HCT00 RESULT:FAULT Pin11_SA0 (G4 OUT stuck-LO) FULL_BAD:192/256 SIG:000011101110
```

## LEDs

| LED | Pin | Meaning |
|---|---|---|
| Green (PASS), on the breadboard | PB12 | last test passed |
| Red (FAULT), on the breadboard | PA8 | last test failed (fault, class, unknown or wrong chip) |
| LD2, green, on the NUCLEO | PA5 | busy: on while a vector is applied in PC mode, blinks during the full check |
| Power LED, on the breadboard | supply rail | breadboard has power |

Both result LEDs turn off when a new chip is selected or a new PC test starts.

## Serial protocol (PC mode)

The ST-LINK virtual COM port runs at 115200 baud, 8 data bits, no parity, 1 stop bit. Commands are ASCII lines ending in `\n` (or `\r`), at most 63 characters. Every reply is one line.

| Command | Reply | Effect |
|---|---|---|
| `PING` | `PONG` | link check |
| `SEL:<0-5>` | `SEL_OK`, or `ERR:SEL` | selects the chip (0 = 74HCT00, 1 = 02, 2 = 04, 3 = 08, 4 = 32, 5 = 86); OLED shows `PC MODE` / `Testing...`, LEDs off |
| `CFG:<14 chars>` | `CFG_OK`, or `ERR:LEN` | sets the direction of each DIP pin, pin 1 first: `I` = board drives (chip input), `O` = board reads (chip output), `X` = unused |
| `V:<bits>` | `R:<bits>`, or `ERR:VLEN` | applies one vector: one character per `I` pin in DIP order; the reply has one character per `O` pin in DIP order |
| `RES:PASS` | `RES_OK` | OLED shows `PASS` / `PC verified`, green LED |
| `RES:FAULT:<text>` | `RES_OK` | OLED shows `FAULT` and the text, red LED |
| `RES:UNKNOWN:<signature>` | `RES_OK` | OLED shows `UNKNOWN` and the signature, red LED |
| `RES:VERIFY_FAIL:<n>/<N>` | `RES_OK` | OLED shows `FAULT` / `Bad n/N`, red LED |
| anything else | `ERR:CMD` | |

The board waits 1 ms after setting the inputs of each vector before reading the outputs. A typical PC session:

```
> PING
< PONG
> SEL:0
< SEL_OK
> CFG:IIOIIOXOIIOIIX
< CFG_OK
> V:11111111
< R:0000
> V:01010101
< R:1111
> V:10101010
< R:1111
> RES:PASS
< RES_OK
```

The board replies to `SEL` and `RES` only after it has redrawn the OLED (about 0.3 s), because the UART is polled; the PC tools allow for this.

## Pin handling

Before any reconfiguration the firmware parks all twelve chip lines as plain inputs, so no pin is driven against the chip while directions change. Lines that read chip outputs use the internal pull-down, so a dead or open output reads 0 instead of floating. The power positions (DIP 7 and 14) are never driven.

## I2C bus recovery and OLED re-initialisation

If the MCU resets in the middle of an OLED transfer, the SSD1306 can hold SDA low and the STM32 I2C peripheral then reports the bus as busy until a full power cycle. At start-up, and whenever the OLED does not answer before a redraw, the firmware:

1. de-initialises and resets I2C1,
2. switches PB8 and PB9 to open-drain GPIO and clocks SCL nine times by hand,
3. sends a STOP condition (SDA rising while SCL is high),
4. re-initialises I2C1, which returns the pins to their I2C function.

The OLED controller is also re-initialised before every full screen. If the 5 V rail dips (for example when a chip is inserted with power on), the SSD1306 resets itself to "display off"; re-initialising each time brings it back without an MCU reset.
